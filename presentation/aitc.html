The problem

The tester already
did the work.

They clicked through the flow to check it. Writing it up afterwards costs 10 to 20 minutes — and it is the only part a machine could have done.

But the steps are the easy half. Anyone can list clicks. The line you actually judge a test case by is the Then.

When the coupon "AUTUMN20" is applied
And the order is placed
Then the message "This coupon has expired"

this line is the test — and the one that can be invented

Month one

It worked, end to end.

Recorded sessions in, Gherkin / Excel / Jira out — verified live against a real Jira and a real model.

Capture

Nothing is ever lost

The session is stored raw before any model runs, so a bad prompt can never destroy a recording.

Shape

One canonical test case

Structured JSON in the database, never a formatted string. Gherkin, Excel and Jira are all renderings of it.

Review

A dashboard, and versions

Review, edit and export — every edit kept as a new version, so the model's original always survives.

Checks

A deterministic critic

Plain Python, no second model call, surfacing advisory review questions with proposed answers.

Pipeline

Three passes, not one call

Analyse the session, author each scenario, judge the result — because one call always chose transcription over judgement.

Measure

An evaluation set

A fixed set of sessions, so every change was measured against it instead of judged by eye.

The ceiling

The model was told about the session.
Nothing could check whether what it wrote
was true of the recording.

We could check the shape of the output. We could not check the truth of it.

Consequence

The expected result had one thin source — the narration. Anywhere it was thin, the model filled the gap by inventing.

Defence 1

A critic written as regexes. It could see a missing value. It could not judge a sentence.

Defence 2

A second model's opinion, clamped to a warning. Advisory. It blocked nothing.

So we rebuilt it — this is AITC

A claim is admissible only if it can
point at the retrieval that produced it.

Not “the text exists somewhere in the recording” — that is a weaker, separate check. It has to have come back from a lookup the model actually performed, while writing this document.

The author

One model.
One conversation.
It goes and looks.

Decide→ Retrieve→ Observe↶

It writes the .feature file itself — it used to emit JSON that a script assembled, which meant no model in this pipeline had ever seen a feature file.

And it decides what is worth checking first, then retrieves to prove it. An agent that may only claim what it already fetched writes about whatever was easiest to get.

get_diff
What changed between before and after — the whole document. The workhorse.
get_snapshot
The full page at an event. Expensive, so used sparingly.
see
The screenshot — for when the text does not settle the question.
get_network
The calls behind an event. The only way to prove a status code.
get_narration
What the tester said. The most direct statement of intent there is.
find_text
Where does this exact string appear across the recording?

Six tools, down from twelve — more tools measurably means worse tool choice.

The gate

A fabricated citation is not something
the model can express.

01

It quotes a literal

An exact string it says it saw. It never supplies a reference, an id, or a citation.

02

We find the retrieval

We search the lookups actually made in this run, re-hash the stored response, and confirm the string is really in it.

03

And check it twice

Independently, against the recording itself. What the agent was shown, and what is true of the session.

the claimAdmissible
Then the message "This coupon has expired" is shown
bound to get_diff · evt_014 · re-hashed · 1 occurrence

Seeing a literal in the summary we handed it is not enough — a summary points at nothing. It has to have come back from a tool.

And be clear about the limit: this proves provenance, not correctness.

When it cannot prove something

It says so, in writing.

Refused — written by the author

“Could not check that the product list narrowed to 9 items — the list was never captured before or after this click.”

Previously the claim was just deleted. So a scenario with no verdict and a scenario whose verdict was invented looked identical on the page.

The judge

Would a QA lead sign this?

A second model, fresh context — it never sees how the author reasoned, because a model shown its own justification defends it. Seven questions. Two of them close holes nothing else looks at:

claim within evidence

Does the sentence claim more than its literal shows? One shipped saying “rejected with a 409 Conflict”, proved by a page message with no 409 in it.

refusal is true

A refusal passes every automated check by definition — it claims nothing. It is the one output that is confident and otherwise entirely unchecked.

Being straight with you

What it cannot do yet.

01 — the ask

The model tier is the binding constraint

  • Free-tier limits are on requests, not tokens: 5/min and 20/day. One recording exhausts a day.
  • Free-tier prompts are training-eligible, so the tool refuses to send anything but a demo or public app. Pointing it at a real internal application needs a paid endpoint with a no-training term.
  • Real pages cost ~20×: 150–172 KB per event against 5–10 KB. One full-page look is 16–18k tokens; one real session came to 168,690 prompt tokens against ~29,000.
02 — output

The assertions are not always meaningful

The tool can bind a verdict to a value that is genuinely present but not specific enough to be worth checking.

It now grades that rather than hiding it — and feeding the grade back to the author is the next step.

03 — evidence

We have not tested it enough

Neither the time nor the quota to run the number of sessions that would settle whether the output is good.

The architecture is right and we have shown it working. The quality is not proven — and we are not going to put a green chart in front of you as if it were.

Asked for, and not shipped

MCP — why the obvious version breaks the rule.

The proposal

Drive a live browser

Point Playwright MCP or the Chrome DevTools MCP at it and let the agent explore the application directly.

Why it does not fit
  • A live browser has no past. Every claim here is checked against a before/after pair from a session that already happened. There is nothing to re-check against.
  • Its retrievals bypass our runner — nothing stored, nothing hashed. The gate would refuse every claim and the rule becomes decorative.
  • Twenty-plus tools at once. We cut ours from twelve to six because more tools measurably means worse tool choice.
The idea

Suggestions, not claims

A live agent cannot be evidence-bound — so do not let it make claims. Let it explore and propose extra cases.

The channel already exists: suggestions sit in their own block, render under an UNVERIFIED heading, and are blocked at the gate from ever becoming assertions.

One seam, where every retrieval is already persisted and hashed. The architecture has the hole shaped for it — designed, not built.
