Recorded session → formal test case Chrome MV3 · Python · 14 validators

Every claim has to point at the evidence that produced it.

A QA tester records themselves using a web app. Out comes a test case written in prose — and not one sentence of it survives unless the tool can show you the retrieval it came from.

The problem

A language model will write you a beautiful test case that is wrong.

Ask one to watch a checkout flow and describe what it saw, and you get fluent, well-formed Gherkin. Some of it is true. You cannot tell which parts, because a sentence that was inferred looks exactly like a sentence that was observed.

That is fatal for test cases specifically. A test case is a claim about how software behaves, and a regression suite full of plausible-sounding claims is worse than no suite — it passes while the product breaks, and people trust it.

So the architecture here exists to serve one rule, and everything else falls out of it.

A claim is admissible only if it can point at the retrieval that produced it, in this run.

Not “the string exists somewhere in the recording” — that is a weaker, separate check. The claim names a piece of text; the system resolves which tool call fetched it, re-hashes the stored response, and confirms the text is still in it.

The system now refuses a claim whose evidence is the tester’s own input.

The lesson that shaped the project

Provenance is not correctness. A claim can be traceable, true, and still prove nothing. Most of the hard engineering here is in that gap.

Capture

It records the accessibility tree, not the screen.

A browser extension watches the tester work. The question is what to write down, and the three available answers produce very different tools.

The accessibility tree is what a screen reader sees: button "Place order" rather than div.btn-x9f. It survives a redesign, it needs no cooperation from the application under test, and — the part that matters — it is already in the vocabulary a test case is written in.

The technical detail

Redaction happens in the browser, before anything is written to disk. A password never reaches the server in the first place; the recording carries <<password>>, and those placeholders become the test’s parameters. There is exactly one exception, and it is stated plainly to the tester: spoken narration cannot be redacted before it is understood, and understanding it is what transcription is — so the audio reaches disk raw, never leaves the machine, and the transcript gets a best-effort pass afterwards.

Attribution happens at assembly, not in the moment. A frame does not know when the next action begins, so a network request that lands late would be attributed to the wrong step — or, if it outlived its settle window, never recorded at all. Frames report observations; a later pass decides which step owns them.

Three clocks, and they disagree. performance.now() is per-document, the service worker has wall-clock time, and the offscreen document holding the microphone is a third. Mixing them silently flattens every timestamp — which kills the idle-gap heuristic, or shifts every spoken sentence onto the neighbouring step and produces a plausible, grounded, wrong expected result.

The pipeline

Draft first. Prove second. Delete what will not prove.

This ordering is the load-bearing decision, and it is the reverse of the obvious one.

The obvious design lets the author claim only what it has already retrieved. That produces a document about whatever was easy to retrieve — an earlier version of this system emitted “the hampers category page is loaded”, which is an assertion that the browser works.

So the author writes freely, with the whole session in front of it and no obligation to have looked anything up. Then a separate stage takes each claim and tries to prove it. What cannot be proved is deleted, not softened.

Why the model is never allowed to cite

The drafter writes a sentence and names the text it believes it saw. It does not — cannot — supply the id of the tool call that fetched it. The binding stage searches the retrievals actually made for a response containing that text.

This is stronger than catching a fabricated citation after the fact: there is no field for one. An early version, before this constraint, invented find_text_0 against an otherwise true claim.

What binding refuses, and why each rule exists

Every one of these was added after a real recording shipped past the gate with the defect in it.

  • The tester’s own input. The “Prix bas à haut” case above.
  • Anything the claim quotes must appear in the evidence. A sentence asserting two things while citing evidence for one is half inadmissible, and the unchecked half is free to be wrong: a “Small Wicker Basket” with a capacity of “5 / 5”, bound only to the basket’s name.
  • “The interface appeared.” The shopping bag panel opens, bound to the panel’s own heading. Grounded evidence that a heading exists.
  • Timestamps, uuids, ad and analytics strings. They pass every check and break the moment someone runs the test.
  • One literal cannot be the whole evidence for two different claims. An aria-live region announcing “Results updated.” supports any claim of its shape whatsoever.

Each rule is calibrated against every claim-and-literal pair the pipeline has ever produced, not against the case that motivated it. A rule that rejects the bad pairs and a few good ones is not a fix; it is a yield cut wearing a fix’s name.

The output

What a tester actually gets.

Prose, and nothing else. No ids, no confidence scores, no traceability comments — those live in a sidecar file and in the machine-readable trace. The feature file is the artifact the tool is judged by, and a provenance line under every step made it unreadable. 

Feature: Order approval

  Orders exceeding a specific monetary threshold require manager approval
  before they can be placed

  Scenario: An order over EUR500 requires manager approval
    Given the tester signs in to the application
    When the tester adds an item to the cart and proceeds to checkout
    And the tester sets the order total to "615"
    Then an alert states that orders over EUR500 require approval

    When the tester tries to place the order without approval
    Then the order is rejected with a conflict error

    When the tester confirms manager approval and places the order
    Then the order is confirmed

Fourteen validators run before this file is written. They check that every claim resolves to a retrieval, that the literal is still in the stored response, that no redaction placeholder leaked, that every recorded event is accounted for exactly once, that the scenario ends on an outcome rather than an action, and that the prose reads like a specification rather than a transcript.

Read these two numbers together, always

A grounding rate of 100% is vacuous for a configuration that claimed nothing. With no retrieval tools at all, this system emits no expected results — so it scores a perfect grounding rate on an empty document. Every rate here is reported beside the count it was computed over. That trap has appeared in five different columns of this project’s own metrics.

The evidence

Does the agency earn its cost?

Three configurations of the same pipeline, over seven recordings made through the real extension. A0 has no retrieval tools. A1 retrieves. A2 adds a critic and a bounded repair loop.

Config Expected results kept Grounded Yield Fabricated Gate, final
A0 — no tools01.000.0000.674
A1 — retrieval141.000.6100.973
A2 — + critic121.000.5201.000

A0’s row is the honest one to sit with. It fabricates nothing — but only because it can claim nothing. With no retrieval there is nothing for a sentence to rest on, so every sentence is deleted. Its perfect grounding rate describes an empty document.

A2 keeps fewer expected results than A1 and ends with a cleaner gate. That is the trade a critic is supposed to make, and it took a specific fix to get there: repair used to replace a proven claim before finding out whether the replacement could be proven.

Retrieval effort tracks difficulty, which is the interesting result

A chain that retrieves the same amount for every step is not an agent; it is a pipeline with a model in it. What you want to see is effort concentrating on the steps that were genuinely hard.

On one recording, retrievals per step read {step_003: 5, step_004: 7, step_006: 10, step_007: 10} — nothing on the steps whose outcome was obvious, ten calls each on the two contested ones. An earlier version mandated a lookup on every step; that lifted the average and collapsed the variance to near zero, making an agent that had stopped adapting look identical to one that never had.

Across nine full runs, 18 of 18 assertions resolve to a retrieval whose stored response still contains the literal.

Prior art

Why not just use the tools that already exist?

The obvious question, and it has a real answer for each.

ToolWhy it does not replace this
Playwright Agents Their planner explores the app itself, which needs credentials and permission to click. Nothing in it observes a human using their own browser, so there is no recording — and no access to intent. An agent exploring a checkout page cannot know which rule on it the business cares about.
Playwright MCP, Chrome DevTools MCP Both drive a browser they control. Their network and console tools are scoped to the last navigation — debugging queries, not a durable session log — so a multi-page recording cannot be reconstructed from them.
rrweb Serialises the DOM so a human can watch a session back. It records that div.btn-x9f mutated; it cannot tell you the node was button "Save invoice".

The gap all three leave is the same one: nothing in the prior art records a browser session into an accessibility-semantic structured format. Session replay records pixels. Test recorders record selectors. Recording role, accessible name, and the evidence behind each change is the actual novelty.

Where it stands

What is true, and what is still weak.

The provenance architecture holds. Nothing reaches a feature file without a retrieval behind it, and that is measured rather than asserted.

The open weakness is which true thing gets asserted. In one run the page snapshot contained both "Medium Wicker Basket" and "13 / 13"; the author asserted the basket’s name. Nothing refused it, because nothing was wrong with it — and a broken capacity counter would not have failed that test.

Choosing what is worth checking is judgement, not provenance, and no validator can reach it. That is the honest edge of the current design.
